Anything a person will use as a secret has to come from a source an attacker cannot predict. Python has two modules for randomness, and only one of them is safe for this. This lesson is about the safe one, and about the two smaller traps that come with it.

Every box below starts with the pieces placed for you. Turn that off once the shapes are familiar.

## What you'll be able to do

- Generate a token with `secrets`, and know why not `random`.
- Work out how many hex characters a byte count produces.
- Hash a token so you can store it without keeping the token itself.
- Compare two secrets in a way that does not leak timing.

## Step 1: A token worth using

`secrets.token_hex` gives you random bytes written as hex characters.

<PyBlanks
  title="A 16 byte token"
  scaffold={`import secrets

token = secrets.@1(16)
print(len(token))`}
  pieces={['token_hex', 'token_urlsafe', 'randbelow']}
  answers={[0]}
  expect="32"
  hint="You asked for 16 bytes, and the answer is the length of what came back."/>

32, because 16 bytes written as hex is two characters per byte. `token_urlsafe(16)` would give you something shorter and slightly stronger per character, because it uses an alphabet of 64 rather than 16.

`random` would give you something that looks just as random and is not. It is seeded from a value an attacker can often work out, and it is built for shuffling cards, not for making secrets.

## Step 2: The byte count, not the character count

This is the trap. The number you pass is bytes, and the length you get back depends on the alphabet.

<PyBlanks
  title="A URL-safe token"
  scaffold={`import secrets

print(len(secrets.token_urlsafe(@1)))`}
  pieces={['12', '16', '24']}
  answers={[0]}
  expect="16"
  hint="Four bytes in three characters. Twelve bytes comes out at sixteen characters."/>

`token_urlsafe(12)` gives 16 characters, because the alphabet packs four bytes into three characters and it rounds up. Ask for a 16 character token and you want `token_urlsafe(12)`, not `token_urlsafe(16)`.

## Step 3: Hash the token, keep the digest

A server should not store the token itself. It stores a digest, and compares digests later.

<PyBlanks
  title="Store the digest"
  scaffold={`import hashlib

digest = hashlib.sha256(@1).hexdigest()
print(len(digest))`}
  pieces={['"local-dev-token"', 'b"local-dev-token"', 'local-dev-token']}
  answers={[1]}
  expect="64"
  hint="Same rule as every hash: it works on bytes."/>

64 hex characters, always, because SHA-256 is 32 bytes and hex writes each byte as two characters. Storing the digest means a database leak does not hand over working tokens.

## Step 4: Compare without leaking

Comparing two secrets with `==` stops at the first difference, which takes slightly longer the more characters match. Over enough attempts that timing is information.

<PyBlanks
  title="Compare safely"
  scaffold={`import hmac

print(hmac.@1("token-abc", "token-abc"))`}
  pieces={['compare_digest', 'new', 'digest']}
  answers={[0]}
  expect="True"
  hint="One of those compares two values without stopping early."/>

`compare_digest` takes the same time whether the first character differs or the last one does. It is a small thing that costs nothing, which is the best kind of security habit.

## Step 5: Read a secret from the environment

A secret in your source code is a secret in your git history. Read it from the environment instead.

<PyBlanks
  title="Is it set?"
  scaffold={`import os

print(os.environ.get("LEARMUX_DEMO_TOKEN") is @1)`}
  pieces={['None', 'True', 'False']}
  answers={[0]}
  expect="True"
  hint="get returns one particular value when the name is not there at all."/>

`os.environ.get` returns `None` when the name is missing, which is why the test reads `is None` rather than `== ""`. An empty string means the variable is set to nothing, which is a different situation from it not being set at all.

## Step 6: A short digest for the screen

Digests are 64 characters, which is too long to show. Print the first eight.

<PyBlanks
  title="First eight"
  scaffold={`import hashlib

print(hashlib.sha256(b"local-dev-token").hexdigest()@1)`}
  pieces={['[:8]', '[0:8:2]', '[8:]']}
  answers={[0]}
  expect="0cd48eed"
  hint="A slice from the start, up to but not including position eight."/>

`0cd48eed`. Eight characters is enough to tell two digests apart on a screen and short enough to read, which is why every download page shows you a short one.

## Step 8: A mistake to find

The code runs and prints something, but the number is wrong. Press Run and see.

<PyCell
  variant="fix"
  title="Find the mistake"
  expect="32"
  hint="The argument is bytes, and the answer is hex characters. Two per byte."
  code={`import secrets

token = secrets.token_hex(8)
print(len(token))`}
  solution={`import secrets
token = secrets.token_hex(16)
print(len(token))`}
/>

It prints 16, not 32. Nothing raised, so the only way to notice is to know that a hex digest is twice as long as the bytes it came from. That is exactly the kind of quiet mistake a test catches and a person does not.

## Quick reference

| Piece | What it does |
| --- | --- |
| `secrets.token_hex(n)` | n bytes as 2n hex characters |
| `secrets.token_urlsafe(n)` | n bytes as a URL-safe string |
| `random` | not for secrets, ever |
| `hashlib.sha256(b"...")` | a digest, which needs bytes |
| `.hexdigest()` | always 64 hex characters for SHA-256 |
| `hmac.compare_digest(a, b)` | compare without leaking timing |
| `os.environ.get("NAME")` | `None` when it is not set |
| `digest[:8]` | a short digest for a screen |
